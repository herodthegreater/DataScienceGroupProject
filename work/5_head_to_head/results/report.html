Comparison rules and data audit

The raw dataset has 114,000 rows. The shared cleaned table has 45,046 unique track IDs, with 36,037 training tracks and 9,009 test tracks. All 14 predictors are present. The target is the five-class parent genre. Popularity, original genre tags, artist/title metadata and track IDs are excluded from model predictors.

Each prediction file contains exactly the saved test IDs once. The code aligns by track ID, checks truth and metadata against clean_songs.csv, and reads probabilities by named class columns. It verifies finite values in [0,1], row sums of one and consistency between predicted labels and maximum probability. The probability order is electronic, hiphop/rnb, latin, pop, rock. Both supplied files already have the same order, but the evaluator also accepts reordered rows and columns safely.

The baseline class is chosen from training labels only. Models, hyperparameters and the shared data are fixed. No tuning, threshold selection or feature selection uses the test set. The saved split also matches a read-only reconstruction of the foundation's StratifiedGroupKFold assignment. Full artist credit strings have zero overlap across train/test and across each training fold boundary.

Artist limitation: splitting the semicolon-delimited credits into individual artist names reveals 2,401 shared tokens. 5,072 of 9,009 test tracks (56.3%) have at least one such artist in training. The statement “all test artists are unseen” is too strong. Use “full artist credit groups are separate.” Matching trims whitespace and preserves credited case, keeping names such as LiSA and LISA distinct. This token check is approximate name matching, not identity resolution.

The foundation's mapping comments describe removing some genres after poor rock performance. They do not establish which evaluation informed that choice. Historical test independence cannot be established from the snapshot. This section reuses the frozen inputs and makes no such data or modeling changes.

RF correctly predicts 5,768 tracks, compared with 5,131 for LR and 2,730 for the majority baseline. The forest reduces LR's test errors by 16.4%. Accuracy counts all songs equally. Macro precision, recall and F1 first calculate a score for each genre and then average the five scores equally. Macro F1 is the mean of per-genre F1 values, not the F1 of macro precision and macro recall. Zero-division scores are defined as zero.

ROC-AUC uses the saved five-column probabilities and macro one-vs-rest averaging. It measures ranking of each genre against the rest. It differs from accuracy at the largest-probability decision rule. The constant baseline has AUC 0.5 for every genre.

Permutation importance measures predictive reliance. Correlated features can share importance, and shuffling can create unusual feature combinations. The feature drops are not additive and do not decompose the forest's accuracy gain. These results do not identify causes or justify feature selection on the test set.

Does the gain justify the complexity?

For accuracy on this shared genre-classification task, yes. RF adds 637 correct tracks, improves every macro metric and gains F1 in every genre. LR remains easier to explain: its fitted classifier has 70 feature coefficients and 5 intercepts after standardization. The committed forest recipe uses 300 decision trees with a minimum leaf size of 5. The shared comparison does not establish that every part of the extra complexity is necessary.

The forest has 1,784,632 total tree nodes, median tree depth 27 and maximum depth 36. Using the same pickle protocol without compression, the forest serializes to 185.7 MB and the LR pipeline to 2.3 KB. Serialized size measures this representation, not peak process memory.

For the same 9,009-song batch, median prediction time over five warmed-up runs was 0.0021 seconds for LR and 0.256 seconds for RF. Both used one worker and one native thread in the same environment. These are indicative local timings, not production benchmarks. LR's refit took 0.115 seconds. The original RF training wall time is unavailable because the supplied model was already fitted; load time is not treated as training time.

The improvement supports the forest when predictive accuracy is the priority. It does not establish acceptable minority-genre coverage or a deployment cost-benefit optimum. The class-weighted forest in the reference deck is a separate cross-validation experiment and is excluded from the frozen test comparison.

Professor questions you can answer

Why compare on exactly the same songs?
Otherwise a difference could come from an easier test set. Matching IDs makes the comparison paired.
Why use macro F1?
Electronic has far more tracks than hip-hop/R&B. Macro F1 gives each genre one equal contribution and balances precision with recall.
What does 7.1 points mean?
64.02% minus 56.95%, an absolute gain. It is not a 7.1% relative gain.
Does the forest win everywhere?
It wins every genre's aggregate F1 here, but loses on 584 individual songs that LR gets right.
Why is hip-hop/R&B still difficult?
It is a small class and these audio features overlap with other genres. The errors show poor recall. This comparison alone cannot establish the cause of that weakness.
Why not compare LR coefficients to RF feature_importances_?
Coefficients describe linear class scores after scaling. Forest impurity importance describes tree split reductions. A common permutation score answers the same prediction question for both models.
How do we know the feature comparison uses the right forest?
The confirmed fitted model reproduces every saved test label and probability, with the same feature and class order. We run the shuffles through that model directly.
What does the common feature comparison show?
Both rely strongly on Danceability. Shuffling Acousticness or Instrumentalness causes a larger macro-F1 drop for the forest. These are predictive reliance scores, not causal explanations.
Were all artists held out?
Full credit strings were held out. Individual collaborators can occur in both splits, so that stronger claim would be inaccurate.
Did you tune on the test set?
No. The evaluation used fixed CSV outputs and fixed recipes. Permutation analysis explains verified fixed models and is not used for tuning.
